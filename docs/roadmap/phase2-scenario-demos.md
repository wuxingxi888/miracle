# Phase 2 场景 Demo 提案

## 背景

Phase 2 的目标是把 Miracle UI 从“组件集合”继续推进到“移动业务场景组件与模式库”。这一阶段聚焦场景 Demo 与模板化，先让团队验证业务页面怎么组合组件，再从稳定范式里反推是否需要新增业务组件 API。

这份文档是内部规划，不进入组件库官网导航。官网只展示最终可用内容，例如组件效果、API、代码演示、场景最终示例、主题变量和更新日志。

## 交付顺序

| 顺序 | 场景 | 主要验证点 |
| --- | --- | --- |
| 1 | 搜索筛选列表页 | 搜索、筛选、列表、分页、空态和加载态是否能形成固定组合 |
| 2 | 分步表单页 | 表单校验、分步进度、结构化选择和提交反馈是否顺手 |
| 3 | 上传提交页 | 上传入口、规则提示、图片预览和审核状态是否统一 |
| 4 | 选择器弹层页 | Popup、Tabs、PickerGroup、Cascader、TreeSelect 的组合边界是否清晰 |
| 5 | 结果反馈页 | 成功、失败、无权限、网络异常等结果态是否能复用一套表达方式 |

## 每个场景的完成标准

-   文档里说明适用场景、推荐组合和不适用边界。
-   提供可复制的页面骨架代码，组件示例必须放在代码块中。
-   覆盖空态、加载态、错误态或提交态中的至少两类状态。
-   标出建议使用的主题变量，避免业务页面重新写死颜色和间距。
-   说明什么时候继续组合现有组件，什么时候才考虑抽业务组件。

## 脚手架模板

`create-miracle-cli-app` 在 Phase 2 中应该从“演示一个按钮”升级为“演示一个可扩展业务页”。优先把搜索筛选列表页和上传提交页沉淀进模板说明，让新项目初始化后就能看到 Miracle 的页面组织方式。

模板不需要内置复杂业务逻辑，但需要保留清晰目录：

-   页面级示例放在 `src/pages` 或现有模板约定目录下。
-   主题变量集中维护，不散落在单个页面里。
-   文档 quickstart 说明如何从模板页继续扩展。

## 不做什么

-   不新增业务组件 API，除非同一模式在两个以上场景里稳定复用。
-   不把 demo 写成完整业务系统，避免让文档承担后端数据、权限和流程编排。
-   不优先追求大而全的桌面后台能力，继续保持 Vue 3 移动 H5 场景定位。

## 从范式到组件

如果某个场景组合在真实项目中反复出现，再进入组件提案。提案至少回答：

-   这个组件替代了哪组重复组合。
-   它的最小 API 是什么。
-   它是否可以通过主题变量完成视觉定制。
-   它是否需要独立测试、SSR 快照和文档 demo。

候选组件可以先记录为 `FilterBar`、`Result`、`UploadPanel`、`PageScaffold`、`FormStep`，但 Phase 2 只负责验证模式，不急着稳定这些名称。

## 验收方式

-   官网导航不出现内部规划页。
-   场景组合页只展示最终可用的组合示例，不跳转内部路线图。
-   文档测试覆盖规划文档存在性和官网导航边界。
-   站点构建通过，用户可见页面只呈现已成型内容。
